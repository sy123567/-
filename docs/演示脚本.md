# 「行迹应变」演示脚本（约 10–12 分钟）

> 一句话定位（开场就说，全场记住这句）：
> **这不是一个行程记事本，而是一个「行程中断恢复系统」——外部世界变了，行程能自己发现、自己算出替代方案、并让全组人一起决定改成什么样，且每一步都可回退。**
>
> 补一句（第二个记忆点）：**全程有一个懂这个平台的助手陪着——它答的不是网上的泛泛攻略，而是站内真实的社区内容和功能入口。**

---

## 0. 演示前 5 分钟准备（照做即可）

```bash
# 后端
cd <项目根目录>
export DB_HOST=localhost DB_USER=root DB_PASSWORD=你的密码
./mvnw spring-boot:run

# 前端（另开一个终端）
cd frontend && npm ci && npm run dev
```

检查清单：

- [ ] 浏览器开三个标签：**A 群主**、**B 成员**（用无痕窗口登录另一个账号）、**C Swagger**（`http://localhost:8080/swagger-ui.html`）。
- [ ] A、B 属于同一个小组、同一个行程，行程里至少 4 个节点，其中 1 个是**露天景点**（后面要让它被天气命中）。
- [ ] 提前把「攻略社区」里放 2–3 篇攻略（智能助手要检索它们）。
- [ ] 窗口最大化，浏览器缩放 100%，关掉所有通知弹窗。
- [ ] 准备一句兜底话术：如果外部 API（天气/地图/AI）当场抽风，就说「服务端做了降级：拿不到实时数据时按当地常年同期推算展示，功能链路不断」——这本身就是一个加分点，不要慌。

## 1. 开场 30 秒：讲清楚问题，而不是讲功能

> 「多人出行最难的不是排行程，是**行程被打断之后怎么办**。下雨、封路、临时管制，一个节点废了，后面全乱；更麻烦的是——三五个人，谁说了算？
> 我们做的这套系统覆盖一个完整闭环：**成员约束 → 初始计划 → 外部事件 → 影响分析 → 替代方案 → 集体确认 → 新计划 → 变更回退**。今天我按这条链路从头走一遍。」

（说完这句就直接进系统，别停留在 PPT。）

---

## 2. 第一站：成员约束（30 秒）— 强调「计划是被约束求解出来的」

打开 **成员约束** 页。

要说的：

> 「每个成员有自己的预算上限、体力水平、饮食需求、必访地点。这些不是备注文本，是后面**重规划算法的硬过滤条件**——一会儿你们会看到，系统给出的每一个替代地点，都是先过了预算、可达半径、饮食、天气、事件这五道过滤才敢展示的。」

**加分点**：这里点一句「多人约束求解」，把项目从 CRUD 里摘出来。

---

## 3. 第二站：行程与地图（1 分钟）

打开行程详情。

要说的：

> 「行程是节点序列，带时间窗、坐标和费用。地图和路线用百度地图 API 实算路段时间，不是画个静态图。」

顺手点开一个节点的详情抽屉，展示天气 / 附近推荐 / 备注。

> 「注意这里的天气：如果实时天气服务不可用，我们不会显示 `0°C` 这种缺值，也不会写『示例数据』——服务端会按当地纬度和当月推算常年同期的温度区间正常展示，并标注数据来源，实时服务恢复后自动切回。**演示环境永远是流畅的，但它不是假的，是有依据的降级。**」

---

## 4. 第三站：事件监测与影响分析（1.5 分钟）— 第一个技术高潮

点「同步天气事件 / 执行影响评估」。

要说的：

> 「系统会定时拉取天气预警与城市事件，然后做**时空匹配**：事件有生效时间窗和影响半径，节点有时间窗和坐标，两者在**时间上重叠、空间上命中**才会生成一条影响评估，并给出严重度和风险分。所以这里出现的每一条『受影响节点』，都是算出来的，不是标签写死的。」

**这里一定要讲的一个细节（评委很吃这一套）：**

> 「我们还做了**自清理**：如果这个节点后来被换掉了，原来那条基于旧地点的天气事件会在下一次评估时被自动清除，不会有幽灵数据留在界面上。事件去重键带了 `tripId`，避免两个行程停在同一地点时事件被互相抢占。」

---

## 5. 第四站：替代方案（2 分钟）— 项目的核心

进入 **替代方案** 页。

### 5.1 先讲「一次监测给出的是一组方案，不是一个答案」

> 「一次监测会按不同策略同时生成多套方案——最省钱、最省时间、改动最小等等，每套都标了额外成本、最大延误、改动几个节点。它们共用一个**轮次号**，所以页面上你看到的是**这一次监测给出的全部选择**，包括已经被否决的，决策过程是可追溯的；更早的轮次收进『历史方案』，不会和当前混在一起。」

### 5.2 展开一条节点变更，点开候选（视觉爆点）

> 「点开某个节点的候选——我们把它做成了『念头天空』：每个候选像一个漂浮的想法，缓慢浮动、悬停暂停、被选中后落定成实心卡片。开了系统的『减弱动效』偏好时它会自动静止，是可访问的，不是纯炫技。」

然后立刻转到实质：

> 「视觉之外更重要的是候选**从哪来**：三个来源——AI 提名、地图就近搜索、**其他队伍走过的同类节点**（这一条是社区数据反哺规划）。每个候选都标了距离、评分、评论数、是否室内、亮点标签，比如『室内可避雨』『步行可达』『比原计划便宜』——这些标签是根据原节点实时算出来的，不是固定文案。」

---

## 6. 第五站：节点级投票（3 分钟）— **最大的创新点，重点讲**

这一段是整场的差异化，慢慢讲，让两个浏览器窗口都出镜。

### 6.1 先抛问题

> 「到这里有个真实的产品问题：**候选有 8 个，5 个人，谁点谁说了算吗？** 谁手快谁决定，这在真实出行里会吵架。」

### 6.2 给答案：两层投票

> 「所以我们做了**两层决策**：
> - **方案层投票**：决定要不要采纳整套方案；
> - **节点层投票**：只决定『这一个节点换到哪里』。
>
> 节点层每人一票，可以投某个候选，也可以投『**维持原安排**』，还可以『**弃权**』，每一票都能写**投票备注**——比如『带老人，室内更稳妥』。这样争论是有记录的，不是群里刷屏。」

### 6.3 现场演示（A、B 两个窗口切着来）

1. A 窗口：投「城市博物馆」，备注「下雨，室内更稳妥」→ 票数出现，界面显示 `1/2 已表态`。
2. B 窗口：刷新，能看到 A 的票和备注（WebSocket 推送）→ B 投「弃权」，说明弃权计参与但不计入任何选项。
3. B 改票为同一个候选 → **强调「改票是更新不是新增，数据库里 `(节点变更, 成员)` 是唯一约束，一人一票改到底」**。
4. 落定后，节点变更被写回，方案的额外成本和改动节点数自动重算。

### 6.4 讲规则（这段最能体现思考深度）

> 「落定规则我们写得很克制：**某个选项获得全体成员过半支持，或者全员都表态了且存在唯一领先项**，才落定。**平票一律不落定**——系统不替大家做隐式选择，而是把状态明确显示成『目前平票，等更多人投票』，也支持群主提前计票定案。
> 另外一个安全设计：前端传上来的候选**不被信任**，服务端会重新跑一遍候选生成和校验，同名或 50 米内才认，伪造坐标、过期候选一律拒绝。方案一旦进入整轮投票或被归档，节点投票立即关闭。」

**如果只能记住一句，就是这句：**
> 「这套投票不是『加了个投票按钮』，而是把**多人协作的冲突解决**做进了数据模型和状态机里。」

---

## 7. 第六站：整轮投票 → 应用 → 重算（1 分钟）

在投票中心发起整轮投票，两个窗口各投一票，计票通过。

> 「通过后系统做四件事：把变更写进节点、**重算受影响路段的路线**、把同轮其它方案置为否决并归档、生成一条变更记录。而且会**按新节点重新监测一遍**——因为地点变了，风险要重新算。」

---

## 8. 第七站：变更记录与回退（1 分钟）— 展示「可逆」

打开变更记录时间线。

> 「每条记录带类型（已应用 / 已回退）和**节点级明细**：哪个节点、从哪儿变到哪儿、时间怎么调的。应用方案时我们**存了变更前快照**，所以可以一键回退——回退后节点恢复、路线重算、监测重跑，方案回到『待决策』可以重新投。
> **敢让用户改，是因为改得回来。** 这是我们把它当成『系统』而不是『功能』来做的地方。」

现场点一次回退，让行程真的变回去，再说一句：「这一步在演示里最有说服力。」

---

## 9. 第八站：全局旅行智能助手（2 分钟）— 第二个创新点，认真讲

先说清楚它不是「接了个 ChatGPT」：

> 「这个助手是**全局悬浮**的，任意页面右下角都能唤起，`Esc` 关闭，不打断你当前在做的事。它要解决两类问题：**去哪玩**，和**这个功能在哪**。」

### 9.1 三条回答路径，现场各演一次

1. **旅游推荐** —— 问「上海三天适合去哪玩？」
   > 「它先在**攻略社区**里检索——按标题、城市、主题、标签、正文做关键词命中打分，命中多的、评分高的排前面，取前三篇，**把这些真实攻略作为上下文再交给大模型**。所以它答的是**我们平台里真实存在的攻略**，还会把攻略卡片一起返回，可以直接点进去。这是一个小型的站内 RAG，不是让模型自由发挥。」

2. **目录导航** —— 问「怎么解散小组？」或「事件监测在哪看？」
   > 「站内维护了一份**功能目录**（页面名 + 路径 + 说明 + 关键词），问功能位置时直接命中并给出可点击的入口。这份目录同时也作为大模型回答的事实依据，防止它编出不存在的页面。」

3. **降级** —— 断网 / 没配 Key 的情况
   > 「模型不可用时，退回到纯站内素材的规则回答，助手**永远有答案**。响应里带一个 `source` 字段标明这次是 `ai`（模型生成）、`local`（站内攻略与目录命中）还是 `offline`（兜底），界面上也会显示来源，用户知道答案从哪来。」

### 9.2 讲两个工程细节（这是区别于「调个 API」的地方）

> 「第一，**所有模型调用都在服务端完成，API Key 不会下发到浏览器**——前端只调我们自己的 `POST /api/ai/assistant`。
> 第二，**回答是有据可查的**：返回体里除了文字，还带命中的攻略列表和导航链接，用户可以点进去核对，而不是只能相信一段话。」

### 9.3 一句话收这一段

> 「这个助手把**社区内容**、**站内功能目录**和**大模型**三样东西缝在了一起：社区解决『答案是真实的』，目录解决『答案是可执行的』，模型解决『表达是自然的』，任何一环挂了都还有降级路径。」

## 10. 第九站：协作与治理（40 秒，快速带过）

- 群聊 / 好友 / 攻略社区 / 预算分账：一句话带过，「协作闭环是完整的」。
- 权限：**数据看板不在普通用户导航里**，`/admin` 路由前端有守卫，后端 `GET /api/admin/stats` 还会再校验一次管理员身份，非管理员 403。
  > 「**前端隐藏只是体验，后端校验才是安全**——两层都做了。」
- 生命周期：删除行程（仅群主，级联清掉节点、事件、影响、方案、投票、变更记录、费用、讨论）、成员退出、群主解散。
  > 「删除这类操作最容易在真实数据库里炸外键，我们是按依赖顺序显式清理的，并且写了顺序断言的单元测试。」

---

## 11. 收尾 40 秒：把创新点收成 5 条

> 「总结一下，这个项目和普通的行程管理系统的区别在六点：
> 1. **事件—行程的时空匹配**：不是打标签，是时间窗 + 影响半径的实算，还带自清理和跨行程去重；
> 2. **多策略重规划**：一次监测同时给出多套方案，按轮次归档，决策过程可追溯；
> 3. **两层协作决策**：方案层 + 节点层投票，支持弃权、维持原安排和投票备注，平票不做隐式决定；
> 4. **可逆的变更闭环**：变更前快照 + 节点级明细 + 一键回退 + 回退后重新监测；
> 5. **站内 RAG 智能助手**：全局悬浮入口，先检索社区攻略与功能目录、再把它们作为上下文交给模型，回答带来源标记和可点击的攻略/页面链接，模型不可用时自动降级；
> 6. **工程可靠性**：候选服务端二次校验、密钥不出后端、权限双层校验、外部服务不可用时有依据地降级。
>
> 一句话：**我们解决的是『计划赶不上变化』之后的那一段。**」

## 12. 预判提问与标准答案

**Q：这和携程/马蜂窝有什么区别？**
> A：他们解决「怎么订」，我们解决「订完之后世界变了怎么办」。我们的核心资产是事件—行程匹配和群体决策状态机，不是内容和交易。

**Q：投票平票了怎么办？会不会卡住？**
> A：平票不落定，界面明确显示为平票状态，可以继续投或改票，群主也能提前计票定案。我们刻意不做隐式 tie-breaker，因为不可解释的自动选择在多人场景里会失去信任。

**Q：弃权算不算同意？**
> A：不算。弃权只计入参与人数，不计入任何选项——这是为了让「我没意见」和「我同意维持原样」被区分开，后者是一个独立的可投选项。

**Q：候选地点是不是写死的假数据？**
> A：三个来源——AI 提名、地图就近检索、其他队伍走过的同类节点，都要过预算/可达/饮食/天气/事件五道过滤再去重。而且用户投上来的候选，服务端会重新生成一次候选列表做校验，前端传什么都不被信任。

**Q：外部 API 挂了怎么办？**
> A：全链路降级。天气按当地常年同期推算并标注来源、地图不可用切路线预览、AI 不可用回退攻略检索与目录导航。系统不会因为第三方不可用而白屏或显示缺值。

**Q：这个 AI 助手不就是调了个大模型 API？**
> A：模型只负责最后的表达。真正的工作在前面两步：先在社区攻略里按标题/城市/主题/标签/正文做命中打分取前三篇，再匹配站内功能目录，把这两份**站内事实**作为上下文喂给模型，所以它不会推荐平台上不存在的攻略、也不会编出不存在的页面。返回体里带着命中的攻略和链接，用户可以点进去核对。模型不可用时退回纯站内规则回答，答案质量下降但功能不断。另外 Key 只在服务端，前端拿不到。

**Q：数据量大了性能怎么办？**
> A：天气/地点结果有 Redis 缓存并带 TTL，事件插入有去重键，方案按轮次归档避免全表扫，关键查询字段上都有索引（见 `docs/sql/schema.sql`）。

**Q：怎么保证代码质量？**
> A：后端 Google Java Format（Spotless）+ 单元测试（候选校验、投票计票、删除顺序等都有覆盖），前端 ESLint + TypeScript 严格构建，CI 上跑全套。

## 13. 时间分配速查

| 段落 | 时长 | 是否可砍 |
| --- | --- | --- |
| 开场问题陈述 | 0.5 min | 不能砍 |
| 成员约束 | 0.5 min | 可砍 |
| 行程与地图 | 1 min | 可压到 30s |
| 事件监测与影响分析 | 1.5 min | 不能砍 |
| 替代方案（多方案 + 候选天空） | 2 min | 不能砍 |
| **节点级投票** | **3 min** | **绝对不能砍** |
| 整轮投票与应用 | 1 min | 可压到 30s |
| 变更记录与回退 | 1 min | 不能砍 |
| **全局智能助手** | **2 min** | 可压到 1 min，别砍 |
| 权限与生命周期 | 0.7 min | 可砍 |
| 收尾六条 | 0.7 min | 不能砍 |

**如果只剩 5 分钟**：事件监测 → 替代方案 → 节点投票 → 智能助手（只演「上海三天去哪玩」这一问）→ 回退，收尾六条照读。
