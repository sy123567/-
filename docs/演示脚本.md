# 「行迹应变」演示脚本（三人分段版，约 12 分钟）

> 一句话定位（王一飞开场就说，全场记住这句）：
> **这不是一个行程记事本，而是一个「行程中断恢复系统」——外部世界变了，行程能自己发现、自己算出替代方案、并让全组人一起决定改成什么样，且每一步都可回退。**

# 第一部分｜王一飞：用户与社区（3 分钟）

> 负责分组：用户管理（§3.2.1）、社区管理（§3.2.5）
> 后端包 `account`、`community`，接口前缀 `/api/account/**`、`/api/community/**`

## 1.1 开场 30 秒：讲清楚问题，而不是讲功能

> 「多人出行最难的不是排行程，是**行程被打断之后怎么办**。下雨、封路、临时管制，一个节点废了，后面全乱；更麻烦的是——三五个人，谁说了算？
> 我们做的这套系统覆盖一个完整闭环：**成员约束 → 初始计划 → 外部事件 → 影响分析 → 替代方案 → 集体确认 → 新计划 → 变更回退**。今天我们三个人按这条链路从头走一遍，我先讲用户和社区这一层，也就是『人和内容从哪来』。」

（说完这句就直接进系统，别停留在 PPT。）

## 1.2 用户体系与鉴权（40 秒）

现场用 A 账号登录一次。

> 「注册登录走 JWT：密码只存 BCrypt 摘要，登录签发 token，后续所有接口都带 token 校验，前端把身份存在受控的 auth 状态里，刷新不掉线。
> 个人设置里可以改资料和改密码——改密码要校验旧密码，**不允许直接覆盖**。
> 这里有一个我们特意做的权限细节：**用户能看到什么，是后端说了算，不是前端藏一藏**。一会儿宋研讲后台数据看板时会展开这一点。」

**加分点**：一句话点出「身份是整个协作系统的地基」——没有可信身份，后面的投票、分账、权限全都不成立。

## 1.3 攻略社区（1 分钟）

打开 **攻略社区** 页。

> 「社区不是一个摆设的内容页，它是我们平台的**数据来源之一**。攻略可以按城市、主题、标签浏览和搜索，可以收藏、评论、评分。
> 检索这块做了多条件组合：标题、城市、主题、标签、正文都可以命中，命中多的和评分高的排前面。」

顺手搜一个城市，展示筛选结果。

> 「为什么要把检索做扎实？因为它有两个下游消费者——**攻略纳用**（我马上演示）和**宋研的智能助手**（他那段会讲）。社区数据在这个项目里是被算法真正读取的，不是只给人看的。」

## 1.4 攻略纳用：把内容变成可执行行程（1 分钟）— 我这段的亮点

选一篇攻略，点「套用为行程」。

> 「这是社区闭环的关键一步：一篇攻略里写的是『第 1 天上午去 A、下午去 B』这种**相对时间**，纳用的时候我们会把相对日期和时间**实例化成真实的 `LocalDateTime`**，落成一条真正的行程和一串节点，之后就可以被约束校验、被地图算路、被事件监测——**和手工排的行程完全同权**。
> 换句话说：社区内容进来之后，会走完整条动态闭环，而不是变成一段只能读的文字。」

**如果只能记住一句：**
> 「我们让社区里的『别人的经验』变成了系统里『可以被算法处理的对象』。」

## 1.5 讨论区与行后游记（20 秒，快带）

> 「行程内有讨论区，成员可以就具体安排留言；行程结束后可以写游记回到社区，形成『消费内容 → 出行 → 产出内容』的循环。」

## 1.6 交接词（照读）

> 「人和内容准备好了，接下来是**怎么把一群人的诉求变成一条真正能走的行程**——祖建明。」

# 第二部分｜祖建明：社交组队与出行规划（3.5 分钟）

> 负责分组：社交组队管理（§3.2.2）、出行规划管理（§3.2.3）
> 后端包 `social`、`planning`，接口前缀 `/api/social/**`、`/api/planning/**`

## 2.1 组队与房间码（40 秒）

打开 **小组** 页，展示房间码加入。

> 「出行小组用**房间码**加入，房间码唯一且可失效，避免陌生人随意进组。小组有群主和成员两种角色，支持转移群主、成员退出、群主解散。
> 为什么要先讲这个？因为**小组决定了『谁有投票权』**——后面宋研讲的两层投票，分母就是这个小组的成员数。组队不是社交装饰，它是决策的授权边界。」

## 2.2 成员约束（40 秒）— 强调「计划是被约束求解出来的」

打开 **成员约束** 页。

> 「每个成员填自己的预算上限、体力水平、饮食需求、必访地点、可用时间。这些不是备注文本，是后面**规划与重规划算法的硬过滤条件**。
> 可用时间会做**交集运算**：取所有人最大的开始日期和最小的结束日期，如果交集为空，系统直接告诉你『这几个人没有共同可行的档期』，而不是硬排一个没人能去的行程。」

**加分点**：这里点一句「多人约束求解」，把项目从 CRUD 里摘出来。

## 2.3 初始方案生成（1 分钟）— 我这段的技术核心

点「按约束生成计划」。

> 「初始方案不是把景点随便串起来：它要同时满足**预算上限、每日体力上限、饮食限制、必访地点必须出现、时间窗不冲突**，再按地理位置聚类，尽量让同一天的节点靠在一起、减少折返。
> 这里还接了一条 AI 辅助的输入：**AI 可以按城市、天数和兴趣提名候选节点**——这部分能力是宋研实现的（`GET /api/ai/plan`），但它产出的节点会进入我**同一条**路线计算和预算校验链路，和手工节点走一模一样的规则。
> 我们特意**不让 AI 单独另起一条行程生成路径**，否则就会出现『AI 生成的行程不受约束检查』这种前后不一致的坑。」

**这句可以背下来：**
> 「AI 负责『想得到』，规划模块负责『算得准』，两边的边界很清楚。」

## 2.4 行程节点与地图路线（1 分钟）

打开行程详情。

> 「行程是节点序列，带时间窗、坐标和费用，可以增删改和调整顺序。地图和路线用百度地图 API **实算路段时间**，不是画个静态图；地图服务不可用时降级为路线预览，链路不断。」

顺手点开一个节点的详情抽屉，展示天气 / 附近推荐 / 备注。

> 「注意这里的天气：如果实时天气服务不可用，我们不会显示 `0°C` 这种缺值，也不会写『示例数据』——服务端会按当地纬度和当月推算常年同期的温度区间正常展示，并标注数据来源，实时服务恢复后自动切回。**演示环境永远是流畅的，但它不是假的，是有依据的降级。**」

## 2.5 预算与分账（30 秒，快带）

> 「行程有预算跟踪和花费登记，结束后按成员分账结算，谁该给谁多少一目了然。这块不难，但它是『多人出行』这个场景里绕不开的一环。」

## 2.6 交接词（照读）

> 「到这里，一条**满足所有人约束的行程**已经排好了。但真实世界不会照着我们的行程走——下面是这个项目最难、也最有意思的部分，宋研。」

# 第三部分｜宋研：监测应变、后台与智能能力（5 分钟）

> 负责分组：监测与应变管理（§3.2.4）、后台与监控管理（§3.2.6）、智能能力管理
> 后端包 `monitor`、`admin`、`ai`，接口前缀 `/api/monitor/**`、`/api/admin/**`、`/api/ai/**`

## 3.1 事件监测与影响分析（1 分钟）— 第一个技术高潮

点「同步天气事件 / 执行影响评估」。

> 「系统会定时拉取天气预警与城市事件，然后做**时空匹配**：事件有生效时间窗和影响半径，节点有时间窗和坐标，两者在**时间上重叠、空间上命中**（Haversine 距离）才会生成一条影响评估，并给出严重度和风险分。所以这里出现的每一条『受影响节点』，都是算出来的，不是标签写死的。」

**这里一定要讲的细节（评委很吃这一套）：**

> 「我们还做了**自清理**：如果这个节点后来被换掉了，原来那条基于旧地点的天气事件会在下一次评估时被自动清除，不会有幽灵数据留在界面上。事件去重键带了 `tripId`，避免两个行程停在同一地点时事件被互相抢占。
> 风险评分是把**严重度、受影响节点占比、成本暴露、时间缓冲**归一化后加权，越接近节点开始时间、风险越高——所以它是会随时间变化的动态值。」

## 3.2 多策略重规划（1 分钟）— 项目的核心

进入 **替代方案** 页。

> 「一次监测会按不同策略同时生成多套方案——最省钱、最省时间、改动最小等等，每套都标了额外成本、最大延误、改动几个节点。它们共用一个**轮次号**，所以页面上你看到的是**这一次监测给出的全部选择**，包括已经被否决的，决策过程是可追溯的；更早的轮次收进『历史方案』，不会和当前混在一起。」

展开一条节点变更，点开候选：

> 「点开某个节点的候选——我们做成了『念头天空』：每个候选像一个漂浮的想法，缓慢浮动、悬停暂停、被选中后落定成实心卡片；开了系统『减弱动效』偏好时它会自动静止，是可访问的，不是纯炫技。
> 视觉之外更重要的是候选**从哪来**：三个来源——**AI 提名**、**地图就近搜索**、**其他队伍走过的同类节点**（社区与行程数据反哺规划）。每个候选都标了距离、评分、评论数、是否室内、亮点标签，比如『室内可避雨』『步行可达』『比原计划便宜』——这些标签是根据原节点实时算出来的，不是固定文案。」

## 3.3 节点级投票（1.5 分钟）— **最大的创新点，重点讲**

这一段让 A、B 两个浏览器窗口都出镜。

### 先抛问题

> 「到这里有个真实的产品问题：**候选有 8 个，5 个人，谁点谁说了算吗？** 谁手快谁决定，这在真实出行里会吵架。」

### 给答案：两层投票

> 「所以我们做了**两层决策**：
> - **方案层投票**：决定要不要采纳整套方案；
> - **节点层投票**：只决定『这一个节点换到哪里』。
>
> 节点层每人一票，可以投某个候选，也可以投『**维持原安排**』，还可以『**弃权**』，每一票都能写**投票备注**——比如『带老人，室内更稳妥』。这样争论是有记录的，不是群里刷屏。」

### 现场演示（A、B 两个窗口切着来）

1. A 窗口：投「城市博物馆」，备注「下雨，室内更稳妥」→ 票数出现，界面显示 `1/2 已表态`。
2. B 窗口：刷新，能看到 A 的票和备注（WebSocket 推送）→ B 投「弃权」，说明弃权计参与但不计入任何选项。
3. B 改票为同一个候选 → **强调「改票是更新不是新增，数据库里 `(节点变更, 成员)` 是唯一约束，一人一票改到底」**。
4. 落定后，节点变更被写回，方案的额外成本和改动节点数自动重算。

### 讲规则（最能体现思考深度）

> 「落定规则我们写得很克制：**某个选项获得全体成员过半支持，或者全员都表态了且存在唯一领先项**，才落定。**平票一律不落定**——系统不替大家做隐式选择，而是把状态明确显示成『目前平票，等更多人投票』，也支持群主提前计票定案。
> 另一个安全设计：前端传上来的候选**不被信任**，服务端会重新跑一遍候选生成和校验，同名或 50 米内才认，伪造坐标、过期候选一律拒绝。方案一旦进入整轮投票或被归档，节点投票立即关闭。」

**如果只能记住一句：**
> 「这套投票不是『加了个投票按钮』，而是把**多人协作的冲突解决**做进了数据模型和状态机里。」

## 3.4 整轮投票 → 应用 → 回退（1 分钟）— 展示「可逆」

在投票中心发起整轮投票，两个窗口各投一票，计票通过。

> 「通过后系统做四件事：把变更写进节点、**重算受影响路段的路线**、把同轮其它方案置为否决并归档、生成一条变更记录。而且会**按新节点重新监测一遍**——因为地点变了，风险要重新算。」

打开变更记录时间线，现场点一次回退。

> 「每条记录带类型（已应用 / 已回退）和**节点级明细**：哪个节点、从哪儿变到哪儿、时间怎么调的。应用方案时我们**存了变更前快照**，所以可以一键回退——回退后节点恢复、路线重算、监测重跑，方案回到『待决策』可以重新投。
> **敢让用户改，是因为改得回来。**」

## 3.5 全局旅行智能助手（1 分钟）— 第二个创新点

先说清楚它不是「接了个 ChatGPT」：

> 「这个助手是**全局悬浮**的，任意页面都能唤起，打开是右半屏抽屉、`Esc` 关闭，不打断你当前在做的事。它解决两类问题：**去哪玩**，和**这个功能在哪**。」

三条回答路径，现场演一到两个：

1. **旅游推荐** —— 问「上海三天适合去哪玩？」
   > 「它先在**攻略社区**（王一飞那块的数据）里检索——按标题、城市、主题、标签、正文做关键词命中打分，取前三篇，**把这些真实攻略作为上下文再交给大模型**。所以它答的是**我们平台里真实存在的攻略**，还会把攻略卡片一起返回，可以直接点进去。这是一个小型的站内 RAG，不是让模型自由发挥。」
2. **目录导航** —— 问「怎么解散小组？」或「事件监测在哪看？」
   > 「站内维护了一份**功能目录**（页面名 + 路径 + 说明 + 关键词），问功能位置时直接命中并给出可点击的入口，同时作为模型回答的事实依据，防止它编出不存在的页面。」
3. **降级** —— 断网 / 没配 Key
   > 「模型不可用时退回纯站内素材的规则回答，助手**永远有答案**。响应里带 `source` 字段标明 `ai` / `local` / `offline`，界面上显示来源，用户知道答案从哪来。」

两个工程细节（区别于「调个 API」的地方）：

> 「第一，**所有模型调用都在服务端完成，API Key 不下发到浏览器**——前端只调 `POST /api/ai/assistant`。
> 第二，**回答有据可查**：返回体除了文字，还带命中的攻略列表和导航链接，用户可以点进去核对。
> 收一句：社区解决『答案是真实的』，目录解决『答案是可执行的』，模型解决『表达是自然的』，任何一环挂了都还有降级路径。」

## 3.6 后台与权限（30 秒）

> 「**数据看板不在普通用户导航里**，`/admin` 路由前端有守卫，后端 `GET /api/admin/stats` 还会再校验一次管理员身份，非管理员 403。
> **前端隐藏只是体验，后端校验才是安全**——两层都做了。
> 生命周期这块：删除行程（仅群主，级联清掉节点、事件、影响、方案、投票、变更记录、费用、讨论）、成员退出、群主解散。删除最容易在真实数据库里炸外键，我们是按依赖顺序显式清理的，并且写了顺序断言的单元测试。」

## 5. 预判提问与标准答案（按归属分答，谁的模块谁接）

**Q：这和携程/马蜂窝有什么区别？** → 任意一人
> A：他们解决「怎么订」，我们解决「订完之后世界变了怎么办」。我们的核心资产是事件—行程匹配和群体决策状态机，不是内容和交易。

**Q：投票平票了怎么办？会不会卡住？** → 宋研
> A：平票不落定，界面明确显示为平票状态，可以继续投或改票，群主也能提前计票定案。我们刻意不做隐式 tie-breaker，因为不可解释的自动选择在多人场景里会失去信任。

**Q：弃权算不算同意？** → 宋研
> A：不算。弃权只计入参与人数，不计入任何选项——为了让「我没意见」和「我同意维持原样」被区分开，后者是一个独立的可投选项。

**Q：候选地点是不是写死的假数据？** → 宋研
> A：三个来源——AI 提名、地图就近检索、其他队伍走过的同类节点，都要过预算/可达/饮食/天气/事件五道过滤再去重。用户投上来的候选，服务端会重新生成一次候选列表做校验，前端传什么都不被信任。

**Q：初始行程是怎么排出来的？只是按距离排序吗？** → 祖建明
> A：不是。要同时满足预算上限、每日体力上限、饮食限制、必访地点、时间窗不冲突，再按地理聚类减少折返；成员可用时间取交集，交集为空会直接提示无共同档期。

**Q：AI 生成的行程会不会绕过你们的约束校验？** → 祖建明（可让宋研补一句）
> A：不会。AI 只负责提名候选节点，节点进入和手工节点完全相同的路线计算与预算/约束校验链路。我们特意不让 AI 另起一条行程生成路径，就是为了避免两套规则不一致。

**Q：攻略纳用是复制一段文字吗？** → 王一飞
> A：不是。攻略里的相对日期时间会被实例化成真实时间戳，落成真正的行程与节点，之后可以被约束校验、算路、被事件监测，和手工行程同权。

**Q：用户权限怎么保证？前端藏起来就行吗？** → 王一飞（宋研补后台部分）
> A：前端隐藏只是体验。`/admin` 前端有守卫，后端接口还会再校验管理员身份，非管理员 403；身份基于 JWT，密码只存 BCrypt 摘要。

**Q：外部 API 挂了怎么办？** → 宋研
> A：全链路降级。天气按当地常年同期推算并标注来源、地图不可用切路线预览、AI 不可用回退攻略检索与目录导航。系统不会因为第三方不可用而白屏或显示缺值。

**Q：这个 AI 助手不就是调了个大模型 API？** → 宋研
> A：模型只负责最后的表达。真正的工作在前面两步：先在社区攻略里按标题/城市/主题/标签/正文做命中打分取前三篇，再匹配站内功能目录，把这两份**站内事实**作为上下文喂给模型，所以它不会推荐平台上不存在的攻略、也不会编出不存在的页面。返回体带着命中的攻略和链接可以点进去核对。模型不可用时退回纯站内规则回答，答案质量下降但功能不断。Key 只在服务端。

**Q：数据量大了性能怎么办？** → 宋研
> A：天气/地点结果有 Redis 缓存并带 TTL，事件插入有去重键，方案按轮次归档避免全表扫，关键查询字段上都有索引（见 `docs/sql/schema.sql`）。

**Q：三个人怎么并行开发、怎么避免互相踩？** → 任意一人（建议王一飞）
> A：按模块分包分工——王一飞 `account`/`community`，祖建明 `social`/`planning`，宋研 `monitor`/`admin`/`ai`，接口前缀也按模块分开；跨模块只走 Service 接口，不互相查表；`common`、配置和 DDL 属于共享区，改动做成独立小 PR。详见 `docs/团队协作与分工开发规范.md`。

**Q：怎么保证代码质量？** → 任意一人
> A：后端 Google Java Format（Spotless）+ 单元测试（候选校验、投票计票、删除顺序等都有覆盖），前端 ESLint + TypeScript 严格构建，CI 上跑全套，`main` 分支受保护、必须走 PR 且需他人 review。
